# Backtesting

`backtest` replays recorded candles through the same code that trades, and reports what
happened. This page is about what its output means — and, more importantly, what it does not.

## The one command

```bash
python -m stop_order_scalp backtest --data tests/fixtures/us30_m1_sample.csv
```

A sample file is committed so the command runs with no setup. It is **synthetic** — the first
two lines of the file say so — and it is generated by
[`scripts/make_sample_candles.py`](../../scripts/make_sample_candles.py) with a fixed seed, so
you can regenerate the identical file.

Point it at real history for anything that matters:

```bash
python -m stop_order_scalp backtest --data us30_2026-03.csv --output reports/march.json
```

| Flag | Effect |
| --- | --- |
| `--data PATH` | required. The command refuses to invent candles |
| `--from` / `--to` | ISO-8601 window; a naive bound is read as UTC |
| `--slippage-points N` | adverse slippage. Negative is refused |
| `--max-cycles N` | stop after N bars |
| `--output PATH` | write the full report, including every bar and trade |
| `--symbol NAME` | override the configured symbol |

The CSV is `time,open,high,low,close`, oldest first, one row per candle. `time` may be epoch
seconds, ISO-8601, or `YYYY-MM-DD HH:MM:SS`. **Lines starting with `#` are comments**, so a
data file can carry its own provenance at the top.

Without a separate M15 file, the direction series is aggregated from the M1 bars. That is
deliberate: the direction filter refuses a timeframe mismatch rather than guessing, and a
replay that fed it M1 bars and was *accepted* would be a look-ahead bug shaped like a result.

## Reading the output

```
trades : {"closed": 19, "wins": 9, "losses": 10, "scratches": 0,
          "win_rate": "0.4737", "open_at_end": 1}
```

| Field | What it is |
| --- | --- |
| `win_rate` | winners ÷ **decided** trades. `null` when nothing was decided |
| `profit_factor` | gross profit ÷ gross loss. `null` when nothing lost |
| `scratches` | closed for exactly nothing — neither a win nor a loss |
| `open_at_end` | still open when the data ran out. Counted, not dropped |
| `exits_by_reason` | how each trade ended, as the venue classified it |
| `max_drawdown` | largest peak-to-trough fall in equity, not first-to-last |

Two fields are `null` rather than `0` on purpose. "No trades" and "every trade lost" are
different facts, and a zero reports the first as the second. Same for a profit factor with no
losses: the ratio is undefined, and `inf` would be an artefact of dividing by zero wearing the
costume of a result.

Every trade in the report comes from `SimulatedBroker.history()` — the venue's own record of
what it closed, written at the moment of closure. Nothing is reconstructed from the plans, and
no exit level is read from an intent. That is not fastidiousness: the dry-run report once
printed `planned 0.4 lots at 40006.3` beside a stop that had moved to 40011.7, and a statistic
computed from intended exits is that same bug with more decimal places.

## What this does not tell you

**A replay measures this rule on this file.** It does not measure the rule. One CSV is one
sample of one market, chosen by whoever selected it, and the number it produces will be quoted
as a result by anyone who does not read this page.

Three further limits, all reported in the output rather than buried here:

- **The symbol specification is a guess.** Point `0.1`, tick value `1.0` per lot, contract
  size `1.0`. Every money figure scales with the tick value, so on a real US30 contract the
  same replay reports a very different number. The guess travels with the report for that
  reason.
- **There is no equity-curve statistic.** No Sharpe ratio, no volatility figure, no expected
  value per trade in the abstract. Each needs a sampling model for the *untraded* periods, and
  a sampled curve is a claim about the future wearing the costume of a measurement.
- **Fills are optimistic in one specific way.** A stop order fills when price crosses it, at
  the level, on the bar that crossed it. Real venues fill with slippage and gaps.
  `--slippage-points` exists for that, and it is adverse only — a negative value would be a
  quiet way to improve every result, so it is refused.

## The sample result, and what it actually says

On the committed fixture: 19 closed trades, 9 winners, 10 losers, +462.00 on 10 000, of which
45.60 was commission. Max drawdown 78.04, profit factor 3.67.

A 47% win rate with a profit factor of 3.7 is not a validated edge. It is one day of invented
prices, and it is published here as a demonstration that the command works, not as a result.
The number to watch is the win rate: below 50%, which is what a stop-and-target system
trailing its stop to break-even should look like on data it has never seen.

## Reproducibility

The same command on the same file gives the same answer, every time:

```bash
python -m stop_order_scalp backtest --data tests/fixtures/us30_m1_sample.csv
python -m stop_order_scalp backtest --data tests/fixtures/us30_m1_sample.csv   # identical
```

This is not free, and it was not free the first time. A replay is a *second run* over recorded
data, which is exactly the shape in which Phase 9's idempotency defect survived 1116 tests: one
run, one fresh directory, nothing shared. So a replay's ledger is in memory and always has
been — see the note in the output. `state.path` applies to the trading path, not to a replay,
because a replay's venue is rebuilt on every call and a persisted ledger would outlive the
venue it describes.

If a replay ever stops being repeatable, that is a regression with a known cause. Do not work
around it.
